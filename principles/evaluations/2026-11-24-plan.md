## Decisions (settled 2026-11-24)

Each decision was made from the code, the live data, and research. The
reasoning is kept here so it can be revisited.

### D1: Disable `pg_graphql`: **yes** (PR 1)

- **Nothing uses it.** There are no GraphQL calls in `src/` or the edge
  function; `supabase-js` talks to the REST Data API (PostgREST), and the
  dashboard's table editor doesn't need it either.
- **Supabase itself has moved away from it.** It's no longer enabled by
  default on new projects, "to reduce the attack surface", and its
  Data API hardening guide says to disable it if you don't use it.
- **It's the source of 20 advisor warnings.** Every table is discoverable in
  the GraphQL schema by `anon` and `authenticated`. RLS still blocks the
  rows, but the schema shape is visible before sign-in.
- **It's reversible.** `create extension pg_graphql` restores it if a
  future feature wants GraphQL.

### D2: Text length limits: **set these** (PR 1b)

Measured on 2026-11-24 across 143 recipes, 483 ingredients, and 1152
ingredient rows. Limits are set well above the current longest value, so no
existing row or normal recipe hits them. They follow the repo's existing
pattern (`recipe_notes.body` ≤ 2000, saved plan names ≤ 80 in the UI):
`text` columns with `CHECK (char_length(col) <= N)`, which the Postgres
community recommends over `varchar(n)` because the limit can change later
without rewriting the table.

| Column | Longest today | Limit | Why this number |
|---|---|---|---|
| `recipes.title` | 72 | 200 | ~3× the longest; a title is a line, not a paragraph |
| `recipes.description` | 504 | 2,000 | Matches the note limit |
| `recipes.instructions` | 2,264 | 20,000 | ~9× the longest; leaves room for long imported recipes |
| `recipes.source_url` | 128 | 2,048 | The common practical URL limit |
| `recipes.tags` | 18 tags, 24 chars each | 30 tags, 40 chars each | Via an immutable helper function, since a `CHECK` can't use a subquery |
| `ingredients.name`, `ingredient_aliases.alias_name` | 45 | 120 | Shared catalog that anyone signed in can insert into, so the limit matters most here |
| `recipe_ingredients.notes` | 91 | 500 | |
| `recipe_ingredients.quantity`, `unit` | 19, 9 | 50 each | |
| `planned_meals.notes` | (unused) | 2,000 | Matches the note limit |
| `saved_plans.name` | 10 | 80 | Matches the existing `maxLength={80}` in the UI |
| `profiles.display_name` | (unused) | 80 | |

The import edge function must trim its output to these limits (PR 2's
output validator), so an AI import can never produce a row the database
rejects.

### D3: Edge function CORS: **an allowlist from a function secret** (PR 2)

- The production site is `https://www.allbluemeals.com`; the bare
  `allbluemeals.com` 308-redirects to it, so it's the only production
  origin a browser sends. The allowlist defaults to that origin plus the
  local dev origins `http://localhost:5173` and `http://127.0.0.1:5173`.
  An optional `ALLOWED_ORIGINS` secret (comma-separated) replaces the
  default, for example to add a preview URL while testing.
- Follow OWASP: echo the request's `Origin` only on an exact match
  (scheme, host, and port), always send `Vary: Origin`, and send no
  `Access-Control-Allow-Origin` otherwise.
- No Vercel preview URLs. Any Vercel user can create a `*.vercel.app`
  host, so a pattern would have to be tied to this project's team slug.
  Add a preview origin to the secret only when testing against production
  Supabase from one.
- **Be clear about what this buys.** The app sends the user's token as an
  `Authorization` header from browser storage, not a cookie, so another
  website can't use a signed-in user's session anyway, and `curl` ignores
  CORS. The allowlist is cheap defense in depth, not the protection. What
  actually limits Gemini cost abuse is per-user rate limiting, which is not
  in this plan; add it if the import is ever opened beyond trusted users.

### D4: Recipe list in the URL: **yes, low priority** (PR 13)

- Today the list's search, filters, page, view, and open tag folder go to
  `sessionStorage` when a recipe is opened, and are restored on the way
  back. Leaving the recipes area clears them
  ([AppWorkspaceLayout](../../src/app/components/AppWorkspaceLayout.tsx#L22)).
  This works, so the gain is moderate: a reload or Back/Forward keeps the
  view, and a user can bookmark "my vegetarian recipes". The data is
  per-user, so links aren't for sharing between people.
- Use the URL + storage pattern from `react-router.md` §2: the URL holds
  the state (`?q=&tag=&sort=&rating=&source=&view=&folder=&page=`). The
  existing session storage stays only to fill in a bare `/recipes` (the nav
  tab back from a recipe), redirecting with `replace`. Update the params
  with `replace` too, so typing and paging don't fill the history and Back
  still leaves the list in one step.
- Keep `location.state.mealSlot` (picking a recipe for the planner) when
  updating params, by passing `state` along with `setSearchParams`.
- Search terms will appear in the URL and browser history. Recipe searches
  aren't sensitive, so that's acceptable.

## Phase 1: Security and database

### PR 1: Rewrite the RLS policies (`db/rls-policy-rewrite`, M)

Clears: bare `auth.uid()` ×10, `public` instead of `authenticated` ×9,
`for all` ×7, unindexed foreign keys ×3, and the GraphQL exposure (D1).

1. Before writing the migration, record the current policies and the
   advisor output, so you can compare them afterwards.
2. New migration `YYYYMMDDHHMMSS_rls_per_operation_policies.sql`:
   - For each owner table (`profiles`, `recipes`, `planned_meals`,
     `saved_plans`) drop the `for all` policy and create four:
     SELECT `using`, INSERT `with check`, UPDATE `using` + `with check`,
     DELETE `using`, all `to authenticated` with `(select auth.uid()) = user_id`.
   - Child tables (`recipe_ingredients`, `recipe_notes`, `saved_plan_meals`)
     get the same four, checking the parent:
     `exists (select 1 from public.recipes r where r.id = recipe_id and r.user_id = (select auth.uid()))`.
   - Catalog: `ingredients` SELECT and INSERT, `ingredient_aliases` SELECT,
     each `to authenticated using (true)` / `with check (true)`, dropping the
     `auth.role()` condition. `ingredient_categories` is already correct.
   - Indexes: `saved_plan_meals(recipe_id)`, `ingredients(category)`,
     `recipe_ingredients(recipe_id, substitute_for)`.
   - `drop extension if exists pg_graphql;` (D1).
   - Do it all in one transaction, so no table is ever without a policy.
3. Apply with `supabase db push`, then run `npm run db:types`. Types
   shouldn't change; commit the file if they do.
4. **Verify:**
   - Both advisors show no `auth_rls_initplan`, `unindexed_foreign_keys`, or
     GraphQL warnings.
   - Check RLS both ways with two test users in SQL (`set role authenticated`
     plus `request.jwt.claims` for each user). Each user sees and changes
     only their own rows, on every table and for every operation. `anon`
     sees nothing.
   - Manually run through the app: sign in, add/edit/delete a recipe and a
     note, plan a meal, save and apply a plan, build a grocery list.
5. Also in this PR, a dashboard step: turn on leaked-password protection
   (Auth → Password security). Note it in the PR description, since it
   isn't code.

**Risk:** a typo in a policy locks users out of a table. The two-user check
in step 4 is what catches it, so don't skip it.

### PR 2: Harden `import-recipes` (`edge/import-hardening`, M)

The function has no tests today, so first split the logic into pure modules
that Vitest can test like the rest of the code.

1. **Friendly errors:** replace `Gemini recipe extraction failed:
   ${errorText…}` with a fixed message. Log the status and a short reason
   with `console.error`, never user content.
2. **Block private hosts:** a `isPublicHttpUrl(url)` check (protocol
   `http`/`https`; reject `localhost`, `*.local`, loopback, private,
   link-local, and metadata IP ranges). Fetch with `redirect: "manual"` and
   check each redirect hop the same way, up to 3.
3. **Byte cap:** stop reading the response body after 800 kB instead of
   reading all of it and then slicing.
4. **Time budget:** stop Gemini retries once about 60 s total has passed,
   and return the rate-limit message.
5. **Validate output:** a validator for the recipe shape (title string,
   ingredient rows, etc.) used in the function before responding, and the
   same check in [importRecipes.ts](../../src/features/recipes/api/importRecipes.ts)
   on the client. Drop malformed recipes and add a warning for each, and
   trim fields to the D2 limits.
6. **CORS (D3):** a `corsHeaders(origin)` helper that reads
   `ALLOWED_ORIGINS` (default: `https://www.allbluemeals.com` plus the two
   local dev origins), echoes an exact-match origin, always sends
   `Vary: Origin`, and is used for every response, including errors and the
   preflight.
7. **Tests:** unit tests for `isPublicHttpUrl`, the validator (including
   trimming to the limits), `corsHeaders`, and the client mapping
   (`api.import.test.ts`). Manually test a real import of a
   normal recipe URL, a `localhost` URL, and a page that redirects.
8. Deploy with `supabase functions deploy import-recipes`.

## Phase 3: Performance

### PR 11: Code-split routes (`app/route-code-splitting`, M)

1. Record the current numbers from `npm run build` (612 kB / 179 kB gzip,
   one chunk).
2. In [AppRouter](../../src/app/AppRouter.tsx), `React.lazy` the route
   pages. Keep `LandingPage` and `AuthPage` in the main chunk (first paint
   for signed-out users), and lazy-load the rest, starting with import,
   generate, saved plans, grocery, and preferences.
3. One `<Suspense>` around the routes, with a fallback that follows
   `LoadingModal`'s timing rules (AGENTS.md). Check that it doesn't
   double up with the sign-in modal. `useHomeReady` still controls when that
   modal closes.
4. Add `src/vite-env.d.ts` typing `VITE_SUPABASE_URL` and
   `VITE_SUPABASE_ANON_KEY`.
5. **Verify:** the chunk warning is gone and the main chunk is much
   smaller (target under 250 kB / 80 kB gzip). Use `vite preview` with a
   throttled network to check that the landing page and the first
   navigation into the app have no visible flash.

   **Outcome (2026-11-24):** route splitting moved nine pages out of the
   main chunk, but measuring per package showed the main chunk was mostly
   libraries every screen needs: `react-dom` ~55 kB gz, the Supabase client
   ~44 kB gz, TanStack Query + React Router ~23 kB gz. The app's own code in
   it was only ~24 kB gz. The 80 kB gz target isn't reachable without
   replacing `supabase-js` with its sub-clients (~15 kB gz saving, not worth
   the risk). Instead, libraries now go in `vendor-*` chunks
   (`manualChunks` in `vite.config.ts`), so the first load is about the
   same, but after a deploy returning users re-download only the ~24 kB gz
   app chunk instead of ~155 kB gz. The size warning is gone.
6. **Tests:** page tests that render routes need to `await` lazy pages
   (`findBy…`).
