# Codebase evaluation against the principles: 2026-11-24

How the code at commit `c881f92` measures up to each file in this folder,
judged against the principles and project rules as of `d279597`. The code
didn't change between those commits; only the rules did. Findings link to
the code. Each one says which principle it breaks and how to fix it.

**Severity:** **High** means fix before building more on top of it.
**Medium** means worth a dedicated small PR. **Low** means fix when you're
next working in that file.

## Method

- Searched all of `src/`, `supabase/functions/`, and `src/styles/` for each
  principle (escape hatches, effects, data flow, selectors, test queries).
  Read the code around every hit before counting it as a finding.
- Read the **live** RLS policies, indexes, constraints, and column types
  from the database (`pg_policies`, `pg_indexes`, `pg_constraint`), since
  migrations show history and the live database shows what actually applies.
- Ran Supabase's security and performance advisors.
- Ran `npm run lint`, `npm run build`, and `npm test`. All pass: **92 test
  files, 1073 tests**. The build warns that the one JS chunk is over 500 kB.
- After the rules changed in `d279597`, re-audited the data flow (TanStack
  Query and React sections): every action hook in `queries.ts`, every
  component that keeps its own pending or error state for a save, and
  every component that imports an `api.ts` module. The other sections'
  code and rules didn't change, so they weren't re-run.

## Top priorities

1. **Rewrite the RLS policies in one migration** (Medium, Supabase 1–2).
   Wrap `auth.uid()`/`auth.role()` in `(select …)`, add `to authenticated`,
   split `for all` into one policy per operation, and add the three missing
   foreign key indexes. It's one mechanical migration that clears 13
   advisor warnings.
2. **Move ingredient search into `ingredients/queries.ts`** (High, React 2 /
   Query 1). It's the only search-as-you-type that bypasses the data-loading
   rule, and it can show stale results.
3. **Harden the import edge function** (Medium, Edge Functions 3–4). Stop
   echoing Gemini's error body, refuse private/loopback hosts, and check the
   response shape on the client.
4. **Split the bundle by route** (Medium, Vite 3). Phones download 179 kB of
   gzipped JS before the landing page can render.
5. **Keep the previous recipe page visible while the next loads** (Medium,
   Query 6). It's a one-line change for a visible UX improvement.
6. **Move actions onto `useMutation`, one feature at a time** (Medium,
   Query 5a). Start with recipe notes (the smallest action hook), and add an
   ESLint rule that stops components importing `api.ts`, so the rule is
   enforced the way the TanStack import rule already is.

## Supabase and Postgres

**What's good.** RLS is enabled on every table. Every policy has both `using`
and `with check`. The schema is well constrained: `CHECK`s on every closed
set and range (meal type, rating, cadence, servings, note length),
`timestamptz` for every timestamp, an explicit `on delete` on every foreign
key, and composite indexes for the main access paths
(`planned_meals(user_id, planned_for)`, `recipe_ingredients(recipe_id, position)`).
All three `security definer` functions set `search_path = ''` and revoke
`execute` from `public, anon`. Client queries never `select("*")`, and there's
a single typed client.

| Sev | Finding | Principle |
|---|---|---|
| Medium | **All 10 user-facing policies call `auth.uid()` / `auth.role()` bare**, so Postgres re-evaluates them for every row (advisor `auth_rls_initplan` ×10). It's harmless at today's size, but it's the most common Supabase scaling problem, and the fix is mechanical. | 2 |
| Medium | 9 of 11 policies target role `public` (anon included) instead of `to authenticated`. `ingredients` and `ingredient_aliases` work around it with `auth.role() = 'authenticated'` in the policy body. They're secure because the conditions fail for anon, but the intent should be in the policy's role (only `recipe_notes` and `ingredient_categories` do this today). | 1 |
| Medium | 7 of 11 policies (every owner table: `profiles`, `recipes`, `recipe_ingredients`, `recipe_notes`, `planned_meals`, `saved_plans`, `saved_plan_meals`) are `for all` instead of one per operation, against Supabase's own guidance. The catalog tables already have per-operation policies. It works for today's owner-only rules, but it hides which check guards which operation, and it means a future rule (such as "notes can't be edited after a day") requires rewriting the whole policy. | 1 |
| Low | Three foreign keys have no covering index (advisor `unindexed_foreign_keys`): `ingredients.category`, `recipe_ingredients(recipe_id, substitute_for)` (only a partial index on `substitute_for` exists), and `saved_plan_meals.recipe_id`. The last one matters most: deleting a recipe sets matching `saved_plan_meals` rows to null, which scans that table. | 3 |
| Low | Free-text columns have no length limit (`recipes.title`, `description`, `instructions`, `ingredients.name`). `recipe_notes.body` already has one (≤ 2000). The shared `ingredients` catalog matters most, since any signed-in user can insert into it. | 3, AGENTS.md storage |
| Low | Auth: leaked-password protection (HaveIBeenPwned) is off. It's a dashboard toggle: [docs](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). | 7 |
| Info | Advisors flag all 10 tables as visible in the GraphQL schema to `anon`. RLS still returns no rows, but the schema shape can be discovered. If the app doesn't use GraphQL (it doesn't), disabling the `pg_graphql` extension removes this surface. | 1 |
| Info | Advisors flag `add_ingredient_alias` and `upgrade_ingredient_category` as `security definer` functions callable by signed-in users. This is intended (AGENTS.md describes both), and they're hardened, so no change is needed. | 4 |

**Suggested migration (one file):** replace each `for all` policy with four
per-operation policies (SELECT `using`, INSERT `with check`, UPDATE both,
DELETE `using`), all `to authenticated` with `(select auth.uid())`. For `ingredients` and
`ingredient_aliases`, use `to authenticated using (true)` and drop the
`auth.role()` check. Add the three foreign key indexes. Afterwards, re-run
both advisors and check RLS both ways (AGENTS.md).
